Aeroplan Anti-Bot Hardening

How our scraper could get caught, why, and exactly what to fix · grounded in the codebase + external research · 2026-06-12

The one-sentence version. The realistic ways we'd get an account flagged aren't exotic — they boil down to logging in too often and typing like a machine. Both are small, contained code fixes. The browser itself already looks 100% real. And United sidesteps the whole problem because it never logs into your account at all.

1. United vs Aeroplan — corrected

Correction (2026-06-12). An earlier draft claimed "United never logs in, zero account risk." That was wrong. Web research + a closer code read show United locked award search behind a MileagePlus login (tested ~Aug 2025, mandatory by late 2025, still in force 2026 — logged-out users see cash fares only, miles/award space is hidden). Settled conclusion: there is no anonymous safe haven — United and Aeroplan both require a personal login for award data, so both carry account-freeze risk. "United-first is safer" is false. The login-velocity + human-typing hardening below applies to both programs. For a low-user-risk product this points to the operator-runs-accounts or crowdsourced-human-searches models — not BYO-on-your-main-account.

2. How we'd actually get caught (ranked)

Tier 1 · highest value

① Login velocity — logging in too often, too fast

When the ~30–40 min session expires, the code re-logs-in instantly, up to ~5 full logins on one account in ~3 hours, with no pause between them. A clockwork "expire → instant re-login" rhythm is the cleanest bot signal there is, and per our own docs it's "the exact thing that freezes accounts."

core/aeroplan_runner.py:42,120,230,247 · cli.py:645 · max_reauths=4, deadline_seconds=None

Tier 1 · highest value

② Scripted typing — "pasted, not typed"

The member #, password, and 2FA code are dropped in all at once via .fill() — one event, zero typing rhythm. Glassbox and others specifically flag fields filled with no per-keystroke timing. Research confirms this is a real, used signal.

core/aeroplan_session.py:386,411 · aeroplan_login_drive.py:1152

Tier 2 · environmental

③ No enforced internet-connection (IP) control

The session uses whatever connection the host has. Fine on a home residential IP (why it works today), but IP reputation is the primary Arkose gate — nothing stops a future cloud/datacenter/VPN run from silently looking like a bot. AeroplanSession has no proxy= param (unlike cookie_farm).

Tier 2 · environmental

④ Machine-uniform login timing

A fixed exactly 3.000 s wait between every login step. Humans don't move on a metronome. SETTLE_SECONDS, aeroplan_login_drive.py:85

Already safe — don't touch
  • Browser fingerprint — real Chrome + headed + real GPU closes WebGL/canvas/audio/font/TLS/HTTP-2. It genuinely looks like a real browser.
  • Request signatures (SigV4) — we never forge or replay them; we read the real site's own signed responses. Nothing to get caught on.
  • Telemetry scripts — we block nothing, so we avoid the "why is this browser hiding?" tell. Only our behavior (①②) needs to look human.
  • Schedule cadence — hard-floored; an Aeroplan job can't run more than ~once / 75 min, so "every 15 min" doesn't apply.

3. Do they really watch the mouse & keyboard? (research)

Short answer: yes, both — but as secondary signals. The primary gates are IP reputation, browser fingerprint, and account warmth. Behavioral biometrics are the tiebreaker on top.

Mouse dynamics
Collected & scored by Akamai, Arkose, DataDome, HUMAN. Secondary layer, applied mainly at login/checkout.
Keystroke / typing
Dwell & flight times collected. "Pasted vs typed" is a real, used tell — a clean signal when present.
Fake mouse (ghost cursor)
Detectable. ML spots too-perfect Bézier curves + automation-injected pointer artifacts. Can raise your score.
For Arkose specifically
Reputation-first. Behavior matters far less than IP + fingerprint + warm session.

The asymmetry that decides what to fix: human typing is cheap, safe, and removes a clean tell → worth doing. Fake mouse movement is high-effort, detectable, and can backfire → not worth doing.

Why we don't use a ghost cursor — it's BOTH reasons

Bottom line: keep ghost cursor off. Neither backend needs mouse movement to pass, and faking it has negative expected value. The research backs the existing decision.

4. How to implement the fixes

① Login velocity Tier 1

  • Cap re-auths 4 → 2. Change DEFAULT_MAX_REAUTHS and the --max-reauths default. (Watches already pass 1.)
  • Default a 90-min deadline at the CLI layer (keep the runner unbounded so unit tests stay clean); add a --deadline-seconds flag.
  • Random 60–180 s cooldown before each re-login. Must use an injectable sleep/RNG, because the re-auth loop is unit-tested with a fake clock — a bare time.sleep would make the suite hang.
# core/aeroplan_runner.py — inject sleep + cooldown, fire AFTER the cap checks
sleep=time.sleep, reauth_cooldown=(60.0,180.0), rng=random.uniform
...
if reauth_cooldown is not None:
    sleep(rng(*reauth_cooldown))     # human pacing before ensure_logged_in()

④ Login-step timing jitter Tier 2

Replace the fixed SETTLE_SECONDS=3 with a small randomized dwell via one helper, used at ~6 login-step call sites.

def settle():                          # instead of time.sleep(SETTLE_SECONDS)
    time.sleep(random.uniform(1.5, 4.0))

② Human typing Tier 1

Swap .fill() for click → clear → press_sequentially(value, delay=random.uniform(80,180)) at the three credential/2FA fields. (One shared 2FA helper covers both email & SMS paths.) No unit tests assert on .fill, so nothing breaks.

5. The small stuff — pro / con each

(There are actually four Tier-3 items, not three — listing them all.)

ItemHow to fixPro / Con
webdriver flag
unverified stealth flag		 Add a context add_init_script forcing navigator.webdriver=undefined + a startup check that logs a warning if it's still set. Pro: survives a Chrome update silently breaking the flag.
Con: a clumsy override is itself fingerprintable — validate against the live wall first.
--max-windows cap
no limit today (≈12)		 Add a --max-windows flag, thread it through the runner. Keep default 12; document ~6 as the safer setting. Pro: fewer windows ⇒ more chance the whole span fits in ONE login (zero re-auths — the biggest win).
Con: a low cap can mean more separate runs (more sessions) for wide ranges unless paced.
viewport
fixed 1280×800 every time		 Best: no_viewport=True so the real headed window drives size/DPR. (Alt: jitter the size per session.) Pro: most realistic — real window dims, no emulation layer, kills the "identical every session" tell.
Con: less deterministic window size (fine here — it's headed-only with a real desktop).
cold-start retry
retries login within seconds		 Add a random 8–20 s backoff before the one retry on creds_rejected. Pro: two back-to-back login attempts is a velocity tell; the pause looks human.
Con: adds up to 20 s latency even when the creds are genuinely bad.
